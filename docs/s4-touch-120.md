# S4 — прокрутка пальцем и 120 Гц: что осталось после TEST11 (vayu, iOS 16.5 20F66)

Дата: 2026-10-28. Железо не запускалось. Источник фактов — лог TEST11
`artifacts/vayu/test11-20261027/run/005834-run.log` (cmdline: `fb_120=1 fb_crop=1 fb_threads=6
fb_swap_fence_ms=20 touch_lat=1 touch_hz=240 touch_report_interval=4166 t120=1 fb_budget=1
fb_queue=3 t120_link=1`). Патчи — `/dev/shm/lead-tasks/S4-patches/`.

## Что показал лог

1. **Драйвер и GPU не предел.** По 36 различным 5-секундным окнам: 3119 кадров из 9973 пришли
   позже 12 мс; из этих 3119 только 438 (14 %) ждали fence GPU больше 4 мс, 30 (1 %) провели
   больше 3 мс в копии, **2652 (85 %) — «neither»**, то есть окно отдало кадр позже vblank само.
   `swaps waited for the frame before` = 0 почти везде: драйвер никого не держал.
2. **Тач доставляется 220–230 раз в секунду всё время, пока палец на экране.** Непрерывные
   касания (`tl: p` с шагом < 30 мс) в TEST11: 220, 221, 231, 229, 220 сэмплов/с; это ровно
   `touch_report_interval=4166`. В ядре ограничения 60 нет.
3. **Прокрутка идёт 120 Гц не всегда, но не из-за 60-Гц потолка.** Для тех же непрерывных
   касаний интервалы `tl: s` (swap handed to the driver): 7.8, 8.2, 8.2 мс (медианы) в трёх
   случаях — это 120 Гц; **33.2 и 32.3 мс (30 Гц) в двух других**, при 187 и 55 сэмплах тача.
   То есть окно иногда остаётся в idle-режиме 30 Гц на весь жест, а не «упирается в 60».
4. **`t120_link=1` не увидел ни одной ссылки прокрутки.** 205 запросов диапазона из Files —
   `48..120, preferred 0`; 114 запросов `setPreferredFramesPerSecond: 60 -> 60` из Preferences
   (78) и MobileSlideShow (36), причём у них `t120_link_scroll()` = −1, то есть ссылка создана
   не через `+displayLinkWithTarget:selector:` уже после нашей подмены. Слов «on a scroll view's
   link» в логе нет ни разу: цель ссылки — не `UIScrollView`, а объект анимации
   (`UIScrollAnimation` / `UIScrollViewScrollAnimation` в UIKitCore).
5. **Рендерер окна не предел по среднему.** `hakios-gl: after N frames: ... 3279–3819 us a
   frame` (среднее с начала), при 8.3 мс периода. Драйвер 1.1–1.6 мс, fence 1.4–2.4 мс.

Вывод: остаток — политика частоты в QuartzCore/UIKit. Либо display idle (30 Гц), либо
velocity-политика прокрутки, либо запрос самой ссылки (preferred 0 / 60). Патчи бьют по всем трём,
каждый — отдельным флагом, чтобы A/B был по одной переменной.

## Флаги

Все — вместе с `t120=1`, независимы друг от друга:

- `t120_idle=1` — 53: дисплей не уходит в 30 Гц. Лечит «весь жест на 30».
- `t120_vel=1` — 124: прокрутка не замедляется из-за низкой скорости. Лечит «медленный скролл
  на 60/80».
- `t120_always=1` — 16: рендер каждый refresh (дороже по питанию; для проверки потолка).
- `t120_frlog=1` — 114+115: собственная диагностика арбитража QuartzCore в лог.
- `t120_link=2|3|4|5` — что отвечать `CADisplayLink`: 2 — ссылкам прокрутки (включая
  `preferred 0`), 3 — всем, кто просил ≥60 или 0, 4 — всем, 5 — ещё и в
  `addToRunLoop:forMode:`. В лог теперь пишется класс цели ссылки.
- `t120_touch=1` — сколько `-[UIApplication sendEvent:]` реально доходит до приложения, раз в 5 с.

## Как проверять (одна переменная за прогон)

```
fb_120=1 ... t120=1 t120_idle=1 t120_frlog=1 t120_touch=1 t120_link=1
```

и в логе:

```
hakios: backboardd: t120_idle=1: CA_DISABLE_DISPLAY_IDLE=1 ...
hakios: SpringBoard: t120_idle=1: ...
MiniIOMobileFramebuffer: N frames in 5000 ms (F a second)     # при пальце F -> 120
hakios: <App>: t120_touch: N events in 5000 ms (X a second)  # X ~ 220-230
hakios: <App>: t120_link: ... [UIScrollAnimation]: ... -> ...
```

Успех: в окне с непрерывным касанием (`tl: p` ≥ 200/с) медиана интервала `tl: s` ≤ 9 мс и
`the frames that came late ... neither` падает. Провал: те же 33 мс при `t120_idle=1` — тогда
idle не в QuartzCore, а в окне/бэкборде, и следующий шаг — `t120_always=1` и `t120_frlog=1`.
